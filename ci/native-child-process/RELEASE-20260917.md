The first packaged artifact, arm64/2in1, passed boot, UI, Rust executable,
21 direct C API cases, and 180-second stability before the remaining packages
were built. Its checksum, commands, and results are in
`validation/arm64-2in1/first-artifact-gate.md` under the archive root. This
order is required by the repository's `AGENTS.md`.

All six archives passed profile and ELF checks, a fresh QEMU boot, account
readiness, Rust executable, UI switching, and 180-second stability. The three
2in1 profiles passed the 21 Native cases, including the empty getter, exact
150 KiB ASCII and Unicode, 16 FDs, both startup APIs, and over-limit rejection.
Phone profiles retain their normal Native child-process eligibility settings,
so the original six-package validation did not claim Native runtime coverage
for phone.

An additional opt-in run against the unchanged arm64/phone archive SHA-256
`94f09d36028dcf610e9a6121abea417cdb0d3b84cae116d110f50cf9488e0171`
enabled `multi_process_model=true` and `max_native_child_process=50` only in
the extracted private system image. It passed 21/21 Native C API cases,
including the empty Ability getter, exact 150 KiB payloads with 16 FDs, both
startup APIs, over-limit rejection, and a successful launch after rejection.
Phone UI switching and 180-second stability also passed. Evidence:
`validation/arm64-phone-native-private-final/validation.json` and
`native-regression/results.log` under that directory. This proves the phone
runtime can run Native child processes when eligible; the distributed phone
archive still has its normal disabled settings. The armv7a and x86_64 phone
profiles have not undergone this opt-in Native runtime test.

ARMv7a runs the 21 cases as separate app launches. The TCG guest may terminate
the foreground test app after multiple consecutive Native child launches; the
single-launch 150 KiB case returns success with all 153600 bytes and both getter
checks. Over-limit rejection followed by a valid launch passes in one process.
This matrix does not prove repeated successful ARMv7a child launches within a
single app process. The arm64 and x86_64 2in1 packages passed that sequence.

The first armv7a/phone cold boot had a `render_service` restart during Settings
UI switching (`validation/armv7a-phone`); a second fresh boot from the same
archive passed all phone checks (`validation/armv7a-phone-retry`). Keep both
records when assessing this profile's graphics stability.
