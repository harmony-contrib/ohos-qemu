# Calendar CRUD + reminder viewer successor assessment

Do not enable the old calendar_main installer after current main_ui: both replace MainAbility/index/module/reminder postimages. Old daily browsing, calendar selection and explicit normal-event CRUD are useful source candidates, but the current viewer has separately validated permission prompts, raw UI IDs, shared storage/revision refresh, provider routing and cancellation contracts that must survive.

A formal second batch should preserve the current reminder route/viewer as the read-only path, and add a browse/edit mode as an explicit new whole-source successor. Keep Ability-owned LocalStorage and revision notifications; preserve legacy persisted URI spelling and current installed notification owner/ohos+hmos metadata. A new Want or superseded/destroyed read must not populate another page. Query/display database fields only; URI fields cannot authorize writes or supply trusted titles/times.

Read browsing must request the existing real READ permission. Direct add/update/delete needs explicit user action and actual WRITE permission, which current MainAbility intentionally lacks in its usedScene. Therefore adding direct CRUD requires a reviewed exact module successor and genuine user grant/deny/cancel handling. Alternatively re-use the current user-confirmed Editor UI for mutations where its public API suffices. Do not silently broaden MainAbility's current READ-only contract or restore the old module verbatim.

Preserve untouched event fields on updates, make unsupported all-day/lunar/recurrence/important event edits visibly read-only, and re-read after submitted mutations; UI destruction cannot cancel an already-submitted provider transaction. Genuine shared Calendar/native lifetime changes, full source-state manifests, event_editor successor acceptance and calendar_provider validation need root-owned integration. Existing viewer checks and IDs remain regression cases.

The second batch should pin new complete postimages and transactional upgrades from the current final state. New tests must execute the real controller/Ability with explicit service doubles, followed by actual SDK source HAP/native CFI and new-package public API/UI validation. Cold/warm instance and reboot behavior remain unproven until those actual runs. This batch supplies no second UI installer and does not claim CRUD is active.
